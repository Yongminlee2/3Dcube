## 1. 배경과 전체 그림

폰 하나로 2×2·3×3·4×4 큐브를 돌리고, 배우고, 힌트를 받을 수 있는 앱을 만든다.
실물 큐브가 없어도 앱 안에서 완결되는 것이 목표다.

전체는 네 덩어리이고, 각각 별도의 스펙과 구현 주기를 갖는다.

| | 내용 | 상태 |
|---|---|---|
| **A. 큐브 코어** | 큐브 엔진, 3D 렌더링, 터치 조작, 섞기, 타이머, 기록 | **이 문서** |
| B. 학습 모드 | 단계별 튜토리얼, 공식 라이브러리, 3D 애니메이션 시연 | 이후 |
| C. 힌트·풀이 | 현재 상태 분석 → 다음 수 안내와 해설 | 이후 |
| D. 출시 | 아이콘, 스토어 등록, 서명, iOS 이식 | 이후 |

B와 C는 A 위에서만 존재할 수 있다. A를 먼저 완성한다.

- 2×2 / 3×3 / 4×4 큐브 엔진
- 3D 렌더링과 회전 애니메이션
- 터치 스와이프 조작, 노테이션 버튼 패드

- 앱 아이콘, 스플래시, 스토어 등록, 서명키, 개인정보처리방침 (Phase D)
- 실물 큐브 상태 입력(카메라 스캔, 수동 색 입력) — Phase C에서 다룬다
- 온라인 기능 일체 (계정, 랭킹, 동기화)
- 광고·인앱결제
- 5×5 이상

## 4. 아키텍처

```
[Presentation]  HomeScreen / PracticeScreen / RecordsScreen / SettingsScreen
       ↓
[Interaction]   TouchController, NotationPad          입력 → Move
       ↓
[Rendering]     CubeRenderer(3D), NetView(전개도)      상태 → 그림
       ↓
[Core]          CubeState, Move, Scrambler, SolveDetector, MoveHistory
                ── 순수 C#, UnityEngine 참조 없음
```

의존은 위에서 아래로만 흐른다. Core는 자기 위의 어떤 것도 알지 못한다.

### 어셈블리 분리

| Assembly Definition | 내용 | Unity 참조 |
|---|---|---|
| `Cube.Core.asmdef` | 엔진 전체 | **없음** (`noEngineReferences: true`) |
| `Cube.Unity.asmdef` | 렌더링·입력·화면·저장 | 있음 |
| `Cube.Core.Tests.asmdef` | Core 유닛테스트 (EditMode) | 없음 |
| `Cube.Unity.Tests.asmdef` | 통합 테스트 (PlayMode) | 있음 |

`noEngineReferences`를 켜두면 Core에 실수로 `using UnityEngine`을 넣는 순간 컴파일이 깨진다.
이 경계는 문서상 약속이 아니라 컴파일러가 강제하는 규칙이다.

**분리하는 이유:**

1. 회전 로직을 Unity 에디터 없이 몇 초 만에 테스트할 수 있다
2. **회전 로직 버그와 렌더링 버그가 섞이지 않는다.** 큐브 앱에서 가장 흔한 시간 낭비가 이 둘을 혼동하는 것이다
3. Phase C의 풀이 알고리즘이 Core만 참조하면 된다

## 5. Core 상세

### 5.1 CubeState

큐브의 상태. **N을 파라미터로 받는 하나의 구조**가 2×2·3×3·4×4를 전부 처리한다.
크기별로 코드를 나누면 같은 버그를 세 번 고치게 된다.

```
class CubeState
    int N                     // 2, 3, 4
    byte[] facelets           // 길이 6 * N * N, 값 0~5 (색 번호)

    static CubeState Solved(int n)
    void Apply(Move m)
    void Apply(IEnumerable<Move> moves)
    CubeState Clone()
    bool IsSolved()
    byte Get(Face f, int row, int col)
```

가변(mutable) 객체로 두고 필요할 때 `Clone()` 한다. Phase C의 풀이 탐색이 상태를 대량으로 굴려야 하므로, 매 회전마다 새 배열을 만드는 불변 설계는 감당이 안 된다.

**칸 색 배열을 고른 이유:** 렌더러와 전개도가 변환 없이 그대로 읽는다. 조각의 위치·방향으로 표현하는 방식은 3×3 풀이에는 유리하지만 N마다 구조가 달라지고, 화면에 그리려면 매번 되돌려야 한다.

#### 면 번호와 색

| 번호 | 면 | 기본 색 |
|---|---|---|
| 0 | U (위) | 흰색 |
| 1 | D (아래) | 노란색 |
| 2 | F (앞) | 초록색 |
| 3 | B (뒤) | 파란색 |
| 4 | L (왼쪽) | 주황색 |
| 5 | R (오른쪽) | 빨간색 |

세계 표준 배색(흰-노랑, 초록-파랑, 주황-빨강이 서로 반대편)을 따른다.
색 값은 팔레트에서 바꿀 수 있지만 **면 번호는 고정**이다.

#### 칸 인덱스 규칙

`facelets[face * N * N + row * N + col]`

각 면을 **바깥에서 정면으로 봤을 때** 좌상단이 (0,0), 행 우선.
"정면으로 본다"의 기준 방향은 다음과 같이 고정한다.

| 면 | 위쪽에 오는 면 |
|---|---|
| U | B |
| D | F |
| F, B, L, R | U |

이 규칙이 흔들리면 회전 표가 전부 어긋난다. 상수로 못 박고 테스트로 지킨다.

### 5.2 Move

회전 한 번을 나타내는 값 타입.

```
struct Move
    Axis axis          // X, Y, Z
    byte layer         // 0 ~ N-1
    byte turns         // 1, 2, 3  (90° 단위)
```

**축의 정의**
- X축 양의 방향 = R면 바깥쪽
- Y축 양의 방향 = U면 바깥쪽
- Z축 양의 방향 = F면 바깥쪽

**레이어 번호** — 축의 양의 방향 끝에서부터 0. 즉 X축 레이어 0은 R면 층, 레이어 N-1은 L면 층.

**회전 방향** — 축의 양의 방향에서 원점을 바라볼 때 시계방향이 `turns = 1`.

이 표현이라야 4×4의 안쪽 층까지 같은 코드로 돈다. 면 이름(R, U, F…)은 엔진이 알지 못한다.

`Apply`는 두 가지 일을 한다.
1. 그 층이 큐브 표면 면과 겹칠 때, 해당 면의 칸들을 90°씩 회전
2. 층을 둘러싼 네 면의 띠 한 줄을 순환

레이어 0과 N-1은 1번이 발생하고, 그 사이 층(4×4의 안쪽)은 2번만 발생한다.

### 5.3 MoveNotation

`Move`와 사람이 읽는 문자열 사이의 변환기. **엔진 바깥에 둔다.**

- 파싱: `"R U R' U'"` → `Move[]`
- 출력: `Move[]` → `"R U R' U'"`
- 지원: 기본 6면(`U D L R F B`), 반시계(`'`), 180°(`2`), 넓은수(`Rw` 또는 `r`), 층 지정(`2R` — 4×4의 안쪽 층)
- 전체 회전(`x y z`)은 상태를 바꾸지 않으므로 Phase A에서는 다루지 않는다. 카메라 회전은 별개다

**면 → Move 변환 규칙:** 표준 노테이션의 면 회전은 "그 면을 바깥에서 봤을 때 시계방향"이다.
축의 양수 끝 면(R, U, F)은 `turns = 1`, 음수 끝 면(L, D, B)은 `turns = 3`으로 대응한다.

### 5.4 Scrambler

무작위 회전을 나열해서 섞는다.

| 크기 | 수 | 사용 면 |
|---|---|---|
| 2×2 | 11 | R, U, F 3면만 |
| 3×3 | 20 | 6면 |
| 4×4 | 45 | 6면 바깥층 + 2층 넓은수(`Rw` `Uw` `Fw` `Lw` `Dw` `Bw`) |

- 직전 회전과 같은 축이면 다시 뽑는다 (`R R'` 같은 무의미한 연속 방지)
- 2×2에서 3면만 쓰는 이유: 반대편 면 회전은 큐브 전체를 돌린 것과 같아서 중복이다
- 테스트 재현을 위해 시드를 지정할 수 있다

**이 방식의 중요한 성질:** 완성 상태에서 회전만 했으므로 **풀 수 없는 상태가 원리적으로 생기지 않는다.**
유효성 검사, 패리티 보정, 재섞기 로직이 통째로 불필요해진다.
(임의의 색 배치를 받아들이는 것은 Phase C의 실물 큐브 입력에서 다룰 문제다.)

### 5.5 SolveDetector

6면이 각각 단색이면 완성. 센터 색을 기준으로 삼지 않으므로 전체 회전된 상태도 완성으로 인정한다.

### 5.6 MoveHistory

적용된 `Move`를 순서대로 쌓는다.

- 되돌리기 / 다시하기
- Phase C의 힌트가 "지금까지 무엇을 했는지" 읽는 통로
- 기록에 저장할 총 회전 수

## 6. Unity 레이어

### 6.1 CubeRenderer

큐비(작은 정육면체)를 N³개 배치하고, 겉으로 드러난 면에만 스티커 판을 붙인다.
4×4도 큐비 64개 수준이라 모바일에서 여유롭다. 색 머티리얼 6개를 공유해 드로우콜을 낮게 유지한다.

**회전 애니메이션의 규칙:**

> 회전이 결정된 **순간에 `CubeState`를 커밋**하고, 화면은 뒤따라간다.

돌아갈 층의 큐비들을 임시 축 오브젝트에 붙여 90° 돌리고, 끝나면 떼어내 제자리 좌표로 스냅한다.
`CubeState`는 애니메이션 완료를 기다리지 않는다.

반대로 만들면(애니메이션이 끝난 뒤 커밋) 빠르게 연속 조작할 때 논리 상태와 화면이 어긋나고, 원인 추적이 매우 어렵다.

- 애니메이션 기본 시간: 90°당 120ms (설정에서 0~250ms)
- 연속 입력은 큐에 쌓아 순서대로 재생
- **큐가 8개를 넘으면 애니메이션을 건너뛰고 즉시 최종 자세로 스냅한다.** 밀린 애니메이션이 끝없이 재생되는 것을 막는다

### 6.2 NetView (전개도 미니맵)

`CubeState`를 읽어 6면을 2D 십자 전개도로 그린다.

배치는 고정한다 — 가로줄에 왼쪽부터 **L · F · R · B**, F 위에 **U**, F 아래에 **D**.

```
      [U]
[L]   [F]   [R]   [B]
      [D]
```

- 접기/펴기 가능. 설정과 무관하게 화면에서 바로 토글
- 3D 큐브가 어느 방향을 보고 있든 전개도의 배치는 고정
- Phase C의 힌트 하이라이트가 얹힐 자리다. **칸 단위로 강조 색을 덧씌울 수 있는 인터페이스를 지금 열어둔다**

### 6.3 TouchController

Phase A에서 가장 까다로운 부분이다.

1. 손가락이 닿으면 광선을 쏴서 **어느 큐비의 어느 면**인지 판정
2. 드래그 벡터를 그 면 위의 두 접선 방향에 투영하고, **투영값이 큰 쪽이 회전축**
3. 닿은 큐비의 좌표로 **어느 층**인지 결정
4. 드래그가 임계값(화면 대각선의 2%)을 넘으면 회전을 시작하고, 손가락을 따라 각도를 미리 보여준다
5. 손을 떼면 45°를 기준으로 가장 가까운 90°로 스냅하거나, 못 미치면 취소하고 되돌린다
6. 큐비를 맞추지 못했으면(빈 배경) 큐브 전체를 굴린다 (카메라 궤도 회전, 상태 변화 없음)

**축 판정은 한 번 정해지면 그 드래그가 끝날 때까지 잠근다.** 드래그 도중 손이 흔들려 축이 왔다갔다 하면 조작이 미끄러진다.

임계값·스냅 각도·최소 드래그 거리는 실기기에서 손으로 맞춰야 하는 값이므로 **ScriptableObject 설정값으로 빼두고 조정한다.**

### 6.4 NotationPad

U / D / L / R / F / B 버튼과 반시계(`'`)·넓은수(`w`) 토글.
4×4에서는 안쪽 층 버튼이 추가로 나타난다.

**스와이프와 같은 `Move`를 만들어 같은 경로로 흘려보낸다.** 입력 경로는 둘이지만 그 아래는 하나다.
설정에서 숨길 수 있다.

### 6.5 TimerService

섞기 → (인스펙션) → 계측 → 완성 자동 감지로 정지.

흐름은 다음과 같다.

1. [섞기]를 누르면 큐브가 섞이고, 인스펙션이 켜져 있으면 15초 카운트다운이 시작된다
2. **첫 회전이 들어오는 순간 인스펙션이 끝나고 계측이 시작된다.** 15초를 넘겨도 카운트다운이 음수로 계속 흐를 뿐, 첫 회전을 기다린다
3. `SolveDetector`가 완성을 알리면 계측이 멈춘다

- `System.Diagnostics.Stopwatch` 기반. 프레임 흔들림의 영향을 받지 않는다
- 인스펙션이 꺼져 있으면 섞은 뒤 첫 회전에서 바로 계측이 시작된다
- **Phase A에서는 DNF와 +2 벌점을 다루지 않는다.** 인스펙션 15초를 넘겨도 벌점 없이 그대로 진행한다

### 6.6 SessionStore

기록을 JSON 파일로 저장한다 (`Application.persistentDataPath/records.json`).

- 세션은 큐브 크기별로 나뉜다
- 기록 하나: `{ 시각, 걸린 시간(ms), 스크램블 문자열, 회전 수 }`
- ao5 / ao12: 최근 5개(12개)에서 최고·최저 하나씩 뺀 평균. 개수가 모자라면 표시하지 않는다
- 저장 실패(용량 부족 등)는 화면에 알리고 앱은 계속 동작한다. 기록 때문에 앱이 죽지 않는다

> ⚠️ **테스트할 때 헷갈릴 지점**
> 안드로이드 자동 백업이 켜져 있으면 **앱을 지웠다 다시 깔아도 기록이 되살아난다.**
> 기록 앱에는 바람직한 동작이라 켜둔 채로 간다. 다만 "분명 지웠는데 왜 남아 있지"로 시간을 버리기 쉽다.
> 깨끗한 상태로 테스트하려면 재설치가 아니라 앱 데이터를 지워야 한다.

### 6.7 ThemeService

다크(기본)와 라이트 두 벌.

- 색은 전부 **ScriptableObject 팔레트**에서 나온다. 코드에 색 리터럴을 쓰지 않는다
- 팔레트 항목: 배경, 표면, 주 텍스트, 보조 텍스트, 테두리, 강조, 그리고 큐브 6색
- 전환은 즉시 반영. 선택은 저장된다
- 초기값은 다크

### 6.8 UI 기술 선택

**uGUI**를 쓴다. UI Toolkit이 아니다.

3D 큐브와 겹쳐 배치되는 화면이고, 실기기에서의 입력·텍스트 동작이 검증되어 있다.
테마 전환은 ScriptableObject 팔레트 교체로 충분히 처리된다.

## 8. 테스트 전략

### Core 유닛테스트 (EditMode, Unity 없이 실행)

큐브 엔진은 **정답을 기계적으로 확인할 수 있는** 드문 종류의 코드다. 여기서 확실히 덮는다.

| 항목 | 내용 |
|---|---|
| 4회전 항등 | 같은 층을 4번 = 원래대로. **모든 크기 × 모든 축 × 모든 층** |
| 역시퀀스 | 임의 시퀀스 + 그 역순 = 원래대로 |
| 섞기 왕복 | 섞은 뒤 거꾸로 풀면 완성 |
| 색 보존 | 어떤 회전 뒤에도 각 색의 칸 수가 정확히 N²개 |
| 노테이션 왕복 | 문자열 → Move → 문자열이 원본과 일치 |
| 알려진 결과 | 3×3에서 `R U R' U'`를 6번 반복 = 원래대로 |
| 완성 판정 | 완성 상태는 참, 한 수만 돌려도 거짓 |
| 인덱스 규칙 | 각 면의 (0,0) 칸이 규정된 위치에 있다 |

### 통합 테스트 (PlayMode)

- 애니메이션 큐: 연속 입력 후 최종 화면 배치가 `CubeState`와 일치
- 큐 넘침: 9개 이상 밀어넣어도 상태와 화면이 일치
- 저장·불러오기: 기록을 쓰고 다시 읽으면 같은 값

### 손으로 확인 (자동화 불가)

실기기(Galaxy S20 Ultra, adb 시리얼 `R3CN50JXF9E`)에서 확인한다.

- 스와이프로 의도한 층이 의도한 방향으로 도는가 — **특히 4×4**
- 큐브를 여러 각도로 돌린 뒤에도 스와이프 방향 감각이 유지되는가
- 빠르게 연속 조작할 때 밀리거나 어긋나지 않는가
- 다크/라이트 두 테마에서 전개도가 읽히는가

## 9. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| **한글 경로 빌드 실패** — Unity 에디터가 `C:\Users\사용자\…`에 설치되어 있다 | 프로젝트는 `C:\workAndroid\3Dcube`(ASCII). Gradle 홈은 기존 `C:\workAndroid\gradle-home-ascii` 재사용. 이 PC에서 이미 여러 번 물린 함정이다 |
| **4×4 스와이프 오조작** — 칸이 작아 의도하지 않은 층이 돈다 | 큐브를 화면에 크게 배치, 터치 판정에 여유 반경. 임계값을 설정값으로 빼고 실기기에서 조정 |
| **축 판정 흔들림** — 드래그 중 회전축이 바뀐다 | 축은 한 번 정해지면 드래그가 끝날 때까지 잠근다 |
| **애니메이션과 상태 불일치** | 상태를 먼저 커밋하고 화면이 따라가는 구조로 원천 차단 |
| **iOS 이식** — Mac이 없어 빌드·검증이 불가능하다 | Android만 빌드한다. 입력·파일 경로 등 플랫폼 종속 부분은 인터페이스 뒤로 격리해 나중에 옮기기 쉽게 해둔다. **이식 가능하게 짜두되, 실제 확인은 Mac이 생긴 뒤로 미룬다** |
| **Android SDK/JDK 미비** | 구현 시작 시점에 확인한다. 추가로 받아야 할 것이 있으면 무엇을 왜 받는지 먼저 알리고 진행한다 |

## 11. 완료 기준

- [ ] 2×2 / 3×3 / 4×4를 스와이프와 버튼으로 자유롭게 돌릴 수 있다
- [ ] 섞기 → 풀기 → 완성 자동 감지 → 기록 저장이 끊김 없이 이어진다
- [ ] 전개도 미니맵이 큐브 상태를 정확히 반영한다
- [ ] 되돌리기·다시하기가 동작한다
- [ ] 다크·라이트 테마가 모두 정상 표시된다
- [ ] Core 유닛테스트 전부 통과
- [ ] PlayMode 통합 테스트 전부 통과
- [ ] 실기기에서 세 크기 모두 부드럽게 동작하고, 손으로 확인할 항목을 모두 통과
- [ ] 아이콘·스토어 등록·서명은 **포함하지 않는다**

## 12. 이후 단계가 이 설계에 기대는 것

Phase A는 다음 두 가지 접점을 미리 열어둔다. 구현하지는 않는다.

- **Phase B(학습)** — 홈의 비활성 [배우기] 버튼, 그리고 `Move` 시퀀스를 받아 큐브에 재생시키는 경로. 공식 시연이 이 위에 올라간다
- **Phase C(힌트)** — `MoveHistory`로 진행 상황을 읽고, `NetView`의 칸 단위 강조로 "여기를 보세요"를 표현한다. 풀이 알고리즘은 `Cube.Core`만 참조하면 된다
