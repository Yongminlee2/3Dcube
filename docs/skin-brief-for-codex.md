# 큐브 스킨 발주서 (코덱스 의뢰용)

이 문서는 이미지/텍스처 기반 큐브 스킨을 코덱스(또는 다른 에이전트)에게
의뢰할 때 그대로 넘기는 스펙이다. 여기 적힌 형식대로 파일을 만들어 주면
클로드가 앱에 붙인다.

## 진행 상황 (2026-08-07)

"우드" 스킨 도착 → 검증 → 통합 완료. `Assets/Resources/Skins/Skin_Wood.asset`,
텍스처는 `Assets/Resources/SkinTextures/wood/`. 나머지 7종(대리석·스틸·은하수·
가죽·콘크리트·크리스탈·홀로그램)은 아직이다. 새 스킨이 도착하면
`-executeMethod CubeEditor.SkinImporter.ImportAll`로 자동으로 붙는다 —
`delivery/skins/<id>/` 규격만 맞으면 코드를 더 안 짜도 된다.

## 지금 상태

앱에는 이미 스킨 시스템이 있다. `Assets/Resources/Skins/*.asset`에 6종
(클래식/파스텔/비비드/톤다운/다크스틸 + 텍스처가 있는 우드)이 들어 있다.
색만 있는 5종은 `Assets/Scripts/Services/Skin.cs`의 `StickerColors`(면마다
색 하나)만 쓰고, 우드는 `StickerTextures`(면마다 이미지)까지 쓴다 —
텍스처가 있으면 재질 틴트를 흰색으로 두고 텍스처를 그대로 보여준다.

이 발주서가 요청하는 것은 **실제 이미지 텍스처를 쓰는 스킨**이다 — 나무결,
대리석, 금속, 은하수처럼 단색으로는 못 만드는 것들. 연결 코드는 우드를
붙이면서 이미 만들었다 — 새 스킨이 규격대로 도착하면 `SkinImporter`를
한 번 돌리는 것으로 끝난다(위 "진행 상황" 참고).

## 반드시 지킬 제약 (하드 룰)

### 1. 여섯 면이 서로 뚜렷이 구분돼야 한다

이 큐브는 **색을 보고 맞추는 물건**이다. 스킨이 화려해서 면 구분이
안 되면 그 스킨은 못 쓴다. 판정 기준:

- 각 면의 "대표색"(텍스처 전체의 평균 색) 여섯 개를 놓고, **모든 쌍**에
  대해 아래 둘 중 하나를 만족해야 한다.
  - 휘도 차이 ≥ 0.12  (휘도 = `0.299*R + 0.587*G + 0.114*B`, R/G/B는 0~1)
  - 또는 HSV 색상각(Hue) 차이 ≥ 25도
- 무채색(회색·검정·흰색 계열)은 두 면 이상 쓰지 않는다. 채도가 낮아지면
  휘도만으로 구분해야 하는데 조명 조건에 따라 위험하다.
- 텍스처 안의 무늬(나뭇결, 대리석 결 등)는 이 대표색 대비 밝기 편차가
  너무 크면 안 된다 — 무늬가 스티커 하나를 두 가지 색처럼 보이게 하면
  "이 칸이 무슨 색이지?"가 헷갈린다. 권장: 무늬 부분의 밝기 편차가
  대표색 대비 ±15% 이내.

### 2. 라이선스

- CC0 또는 상업적 이용·수정·재배포가 명시적으로 허용된 무료 라이선스만.
- 스킨마다 출처 URL과 라이선스 종류를 `meta.json`(아래)에 적을 것.
- 출처가 불명확하거나 라이선스를 확인할 수 없는 이미지는 쓰지 않는다.

### 3. 파일 규격

- PNG, 정사각형, 512×512 또는 1024×1024.
- 파일당 1MB 이하 권장 (APK 용량 때문).
- 이음매 없이 반복되면(seamless tile) 더 좋다 — 스티커가 여러 개 붙어
  있을 때 경계가 티 나지 않는다. 필수는 아니다.

## 요청하는 스킨 목록 (예시 8종 — 다 안 해도 됨, 되는 만큼)

| id | 컨셉 | 비고 |
|---|---|---|
| wood | 나무결 | 6면 각각 다른 나뭇결 톤(연한~진한) |
| marble | 대리석 | 흰 바탕 + 색 다른 결(금색/회색/검정 계열 섞어서 구분) |
| steel | 브러시드 메탈 | 색 틴트를 넣어야 6면이 구분됨 (금속 광택만으로는 다 회색이라 탈락) |
| galaxy | 은하수/우주 | 성운 색을 면마다 다르게 |
| leather | 가죽 | 스티치·엠보싱 무늬, 색은 다르게 |
| concrete | 콘크리트 | 색 틴트 필수(회색만 쓰면 규칙 1 위반) |
| crystal | 크리스탈/보석 | 반투명 느낌의 그라데이션 |
| holographic | 홀로그램 | 각도별 무지개 느낌이되, 평균색은 면마다 뚜렷이 다르게 |

흰색(D면) 자리는 비워두지 않아도 된다 — 밝은 톤이면 되고 순백일 필요는 없다.
U/D/F/B/L/R 순서 자체는 자유지만, 색 배정은 아래 "흰 계열 = D" 관례를
따르면 학습 모드 공식과 안 어긋난다(꼭 지킬 필요는 없음, 권장 사항).

## 파일/폴더 규격

스킨 하나당 폴더 하나. 위치는 아직 저장소에 없으니 아무 곳에나 모아서
전달하면 된다(예: `delivery/skins/wood/`).

```
<skin_id>/
  u.png   d.png   f.png   b.png   l.png   r.png   (스티커 텍스처 6장)
  meta.json
```

`meta.json` 형식:

```json
{
  "id": "wood",
  "displayName": "우드",
  "bodyColorHex": "#2B1B12",
  "faces": {
    "u": { "representativeHex": "#C9A063", "sourceUrl": "https://...", "license": "CC0" },
    "d": { "representativeHex": "#E8D9BE", "sourceUrl": "https://...", "license": "CC0" },
    "f": { "representativeHex": "#8A5A2B", "sourceUrl": "https://...", "license": "CC0" },
    "b": { "representativeHex": "#5C3A1E", "sourceUrl": "https://...", "license": "CC0" },
    "l": { "representativeHex": "#A9713C", "sourceUrl": "https://...", "license": "CC0" },
    "r": { "representativeHex": "#D8B888", "sourceUrl": "https://...", "license": "CC0" }
  }
}
```

- `bodyColorHex`: 큐비 사이 그라우트 색. 스티커보다 한 톤 어둡게.
- `representativeHex`: 텍스처 전체의 평균색을 직접 계산해서 적을 것 —
  하드 룰 1번 검사와 2D 전개도(NetView)·실물 큐브 입력 화면에 그대로 쓰인다.
  이 값이 실제 텍스처 평균과 다르면 화면마다 색이 다르게 보이는 버그가 된다.

## 완료 확인 체크리스트 (제출 전 스스로 확인)

- [ ] 여섯 대표색이 하드 룰 1번(휘도 0.12 / 색상각 25도)을 모두 통과한다
- [ ] 무채색(회색·검정·흰색) 면이 두 개 이상이 아니다
- [ ] 모든 이미지가 정사각형이고 512 또는 1024px다
- [ ] 파일당 1MB 이하다
- [ ] `meta.json`의 `representativeHex`가 실제 이미지 평균색과 일치한다
- [ ] 출처·라이선스가 전부 적혀 있고 상업적 이용이 가능하다

## 전달 방법

폴더를 통째로 (`<skin_id>/` 여섯 장 + `meta.json`) 압축해서 넘기면 된다.
클로드가 받아서 `Skin.cs`에 텍스처 슬롯을 추가하고, 대표색은 NetView·
실물 큐브 입력 화면에, 텍스처는 3D 큐브 재질에 연결한다. 스킨 고르기
화면(`SkinScreen.cs`)의 목록에도 자동으로 나타나게 만든다.
