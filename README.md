# 큐브 연습장

실물 큐브가 없어도 폰에서 2×2 · 3×3 · 4×4 큐브를 돌리고, 배우고, 막히면 힌트를 받는 안드로이드 앱.

- 엔진: Unity 6000.3.18f1 (URP)
- 패키지: `com.ymlee.cube`
- 버전: 1.0.0 (코드 1)
- 대상: 안드로이드 우선 출시, iOS는 이후

---

## 1. 무엇을 하는 앱인가

| 기능 | 내용 |
|---|---|
| **연습** | 2×2/3×3/4×4를 손가락과 버튼으로 돌린다. 섞기, 15초 인스펙션, 타이머, 기록, ao5/ao12 |
| **배우기** | 3×3 LBL 7단계 코스. 설명 · 공식 시연 · 단계별 연습 · 통과 판정 · 진도 저장 |
| **힌트** | 지금 상태에서 다음 수와 그 이유. 전개도에 봐야 할 조각을 강조 |
| **실물 큐브 넣기** | 손에 든 큐브의 색을 입력. 맞출 수 없는 배치는 이유와 함께 거부 |
| **스킨** | 큐브 겉모습 6종(색 5종 + 이미지 텍스처 1종) 중 고르기. 뒤에 보이는 큐브가 바로 미리보기 |

인터넷을 쓰지 않고, 어떤 데이터도 수집하지 않는다.

## 2. 설계에서 정한 것과 그 이유

### 2.1 엔진을 Unity에서 떼어냈다

회전 로직 전체가 `Cube.Core` 어셈블리에 있고, 이 어셈블리는 **`UnityEngine`을 참조하지 않는다**(`noEngineReferences: true`로 컴파일러가 강제).

이유가 셋이다.

1. 회전 로직을 Unity 에디터 없이 몇 초 만에 테스트할 수 있다
2. **회전 로직 버그와 렌더링 버그가 섞이지 않는다.** 큐브 앱에서 제일 흔한 시간 낭비가 이 둘을 혼동하는 것이다
3. 힌트 엔진이 렌더링을 끌고 들어오지 않아도 된다

### 2.2 크기별로 코드를 나누지 않았다

`CubeState`는 N을 파라미터로 받는 하나의 구조다. 2×2·3×3·4×4가 같은 코드로 돈다.
크기마다 따로 짜면 같은 버그를 세 번 고치게 된다.

`Move`도 면 이름(R, U, F…)이 아니라 **축·층·회전량**으로 표현한다. 그래야 4×4의 안쪽 층까지 같은 코드로 돈다. 노테이션 문자열은 별도 변환기가 담당하고, 엔진은 문자열을 모른다.

### 2.3 회전은 좌표를 통째로 돌려서 계산한다

층에 속한 칸을 전부 찾아 좌표째로 90° 돌린 다음 다시 칸 번호로 되돌린다.
이 방식이면 **바깥층(면 전체가 도는 경우)과 안쪽층(띠만 도는 경우)을 따로 처리할 필요가 없다.**

짝수 크기에서 중심이 반정수가 되는 문제는 좌표를 2배로 늘려 정수로 다룬다.

### 2.4 섞기는 "돌리기만" 한다

완성 상태에서 무작위로 회전만 시킨다. 그래서 **풀 수 없는 배치가 원리적으로 생기지 않고**, 유효성 검사·패리티 보정·재섞기 로직이 통째로 불필요해진다.

(임의의 색 배치를 받는 것은 실물 큐브 입력 쪽 문제이고, 거기서는 별도로 검사한다.)

### 2.5 상태를 먼저 커밋하고 화면이 따라간다

회전이 결정되는 **순간에 논리 상태를 커밋**하고, 큐비 트랜스폼은 애니메이션으로 뒤따라간다.
반대로 만들면(애니메이션이 끝난 뒤 커밋) 빠르게 연속 조작할 때 상태와 화면이 어긋나고, 원인 추적이 매우 어렵다.

### 2.6 힌트는 최단 풀이를 내지 않는다

20수짜리 최적 해답은 **왜 그 수를 두는지 설명할 수 없다.** 배우는 사람에게 아무것도 가르치지 못한다.

그래서 힌트는 학습 모드가 가르친 LBL을 그대로 따라간다. 탐색 알파벳도 "위층 돌리기 · 큐브 돌리기 · 그 단계 공식"으로 좁혔다. 이게 속도와 설명 가능성을 동시에 해결했다 — 18개 수를 자유 탐색하면 폰에서 못 쓸 만큼 느리고, 답이 나와도 사용자가 배운 형태가 아니다.

### 2.7 흰색을 아래로 옮겼다

세상의 초보자 강의는 예외 없이 **흰 십자를 바닥에서** 시작하고, 표준 공식(Sune, T-perm 등)은 **마지막 층이 위(U)**라고 가정한다. 처음 팔레트는 흰색이 U에 있어 이 둘과 충돌했다.

면 번호와 좌표계는 건드리지 않고 팔레트 색만 바꿨다. 흰색을 아래로 뒤집으면 좌우가 맞바뀌므로 L이 빨강, R이 주황이 된다.

### 2.8 UI를 전부 코드로 만든다

씬 파일에는 부트스트랩 오브젝트 하나만 있고, 카메라·조명·캔버스·화면을 전부 `Awake`에서 코드로 세운다. 씬/프리팹 YAML을 손으로 고칠 일이 없어 모든 변경이 코드로 남는다.

텍스트는 legacy `UnityEngine.UI.Text`를 쓴다. TextMeshPro를 쓰면 폰트 애셋 임포트라는 설치 단계가 생기고, 한글 폰트 라이선스까지 따져야 한다.

## 3. 구조

```
Assets/Scripts/
├─ Core/                    UnityEngine 참조 없음
│  ├─ CubeCoords.cs         칸(면·행·열) ↔ 격자 좌표
│  ├─ Move.cs               축·층·회전량
│  ├─ CubeState.cs          칸 색 배열, Apply, IsSolved
│  ├─ MovePermutation.cs    회전 하나가 칸을 어디로 보내는지
│  ├─ MoveNotation.cs       문자열 ↔ Move (R, U', Rw, 2R, x y z)
│  ├─ Scrambler.cs          섞기
│  ├─ MoveHistory.cs        되돌리기/다시하기
│  ├─ StageChecker.cs       LBL 7단계 통과 판정
│  ├─ LessonData.cs         코스 내용 (상수)
│  ├─ CubeValidator.cs      임의 배치가 조립 가능한지 일곱 검사
│  └─ HintEngine.cs         다음 수와 이유
├─ Rendering/               CubeRenderer, LayerRotator, NetView, LessonPlayer
├─ Interaction/             SwipeResolver, TouchController, OrbitCamera, NotationPad
├─ Services/                Palette, ThemeService, Skin, SkinService, TimerService, SessionStore, LearnProgress
└─ Screens/                 Home, Practice, Learn, Lesson, Algorithm, Records, Settings, ColorInput
```

**책임 경계** — `CubeCoords`는 좌표 규칙만, `CubeState`는 칸 배열만, `MoveNotation`은 문자열만, `CubeRenderer`는 상태→그림만, `TouchController`는 판정만 안다. 회전은 전부 `LayerRotator` 한 곳을 지난다.

## 4. 개발 일지

### Phase A — 큐브 코어 (2026-08-06)

엔진, 3D 렌더링, 스와이프 조작, 타이머, 기록.

- 좌표계를 먼저 못 박았다. 면 번호 U0 D1 F2 B3 L4 R5, 각 면 좌상단부터 행 우선, X+=R·Y+=U·Z+=F 오른손 좌표계. 이게 흔들리면 회전 표가 전부 어긋난다
- `R U R' U'`를 여섯 번 반복하면 제자리로 돌아오는 테스트가 좌표계·회전·노테이션이 서로 맞는지 한 번에 검증한다
- Core(오른손)와 Unity(왼손)의 차이는 `GridToLocal`의 Z 반전 **한 곳에서만** 처리한다

**여기서 잡은 버그:** 애니메이션 큐에 여러 수를 한꺼번에 넣으면, 논리 상태가 즉시 전부 커밋되므로 뒤늦게 재생되는 애니메이션이 "지금 이 층에 있는 큐비"를 조회할 때 이미 미래 좌표를 읽었다. 큐에 넣는 시점에 대상 큐비를 붙잡아 두도록 고쳤다. 테스트가 오차 0.72로 잡아냈다.

### Phase B — 학습 모드 (2026-08-06)

LBL 7단계 코스, 공식 시연, 진도 저장, 공식 라이브러리.

**여기서 잡은 버그:** 6단계 공식으로 흔히 쓰이는 `U R U' L' U R' U' L`은 모서리를 옮기면서 **방향까지 틀어놓는다.** 이 코스는 "노란 면을 먼저 완성 → 그 다음 자리 맞추기" 순서라, 이 공식을 쓰면 애써 맞춘 노란 면이 깨진다. 방향을 보존하는 A-perm(`R' F R' B2 R F' R' B2 R2`)으로 교체했다.

놓쳤다면 **6단계를 따라 한 사용자가 5단계로 되돌아가는** 앱이 됐을 것이다. 눈으로는 알아채기 어려운 종류다.

각 단계의 연습 시작 상태가 정확히 "앞 단계까지만 통과한" 상태인지, 마지막 층 공식이 아래 두 층을 건드리지 않는지, 설명 글이 말하는 "왼쪽 앞 모서리 고정"이 실제로 맞는지를 전부 테스트로 못 박았다.

### Phase C — 힌트와 실물 큐브 입력 (2026-08-06 ~ 08-07)

`CubeValidator`, `HintEngine`, 힌트 화면, 색 입력 화면.

유효성 검사는 일곱 가지를 본다. 그중 **모서리 비틀림 합(mod 3), 엣지 뒤집힘 합(mod 2), 순열 홀짝**은 눈으로 절대 알 수 없다. 스티커를 떼어 붙인 큐브가 정확히 여기에 걸린다.

힌트는 "따라가면 실제로 풀리는가" 하나로 검증한다. 임의의 스크램블에서 힌트만 따라가 완성에 도달하는지 보는 테스트가 힌트 로직 전체를 덮는다.

**여기서 겪은 것:** 마지막 층에서 힌트가 수렴하지 않아 세 번 고쳤는데 증상이 그대로였다. 알고 보니 **Unity가 갱신되지 않은 옛 컴파일 결과로 테스트를 돌리고 있었다.** 첫 수정 이후 코드가 한 번도 실행되지 않았다. 원인을 보려고 만든 진단 테스트가 애셋 갱신을 일으키자 전부 통과했다.

교훈: 같은 실패가 **글자까지 똑같이** 반복되면, 다음 수정을 시도하기 전에 테스트 총 개수가 늘었는지부터 확인한다.

### Phase D — 출시 준비 (2026-08-07, 진행 중)

앱 이름, 아이콘, 버전, 스토어 문안, 개인정보처리방침.

아이콘은 코드로 그린다(`IconGenerator`). 이미지를 밖에서 가져오지 않으니 출처와 라이선스를 따질 것이 없고, 색을 바꾸려면 숫자만 고치면 된다.

### Phase E — 스킨 (2026-08-07)

큐브 겉모습을 고를 수 있게 했다. 색은 지금까지 `Palette`(다크/라이트 테마)가 들고 있었는데, 스킨은 테마와 독립적으로 골라야 해서 `Skin`/`SkinService`로 분리했다 — `Palette`에서 `CubeBody`·`StickerColors`를 떼어냈다.

**하드 제약 하나만 지켰다:** 스킨이 몇 종류든, 여섯 면은 항상 서로 뚜렷이 구분돼야 한다. 이 큐브는 색으로 푸는 물건이라 스킨이 그 전제를 깨면 앱이 못 쓰게 된다. 재질의 금속성(metallic)을 올리는 것도 시도하지 않았다 — 조명이 거의 평평해서 반사가 없고, 금속성을 올리면 색이 탁한 회색으로 죽는다.

이번에 직접 만든 것은 색만 다른 5종(클래식·파스텔·비비드·톤다운·다크스틸)이다. 나무결·대리석·금속·은하수처럼 이미지 텍스처가 있어야 하는 스킨은 코드로 그릴 수 있는 범위를 넘어서므로 만들지 않았다 — 대신 [`docs/skin-brief-for-codex.md`](docs/skin-brief-for-codex.md)에 발주 스펙(색 구분 하드 룰, 라이선스, 파일 규격)을 적어 뒀다. 이미지가 도착하면 그때 `Skin`에 텍스처 슬롯을 추가한다.

**스킨 고르기 화면은 뒤에 진짜 큐브를 띄운다.** `CubeRenderer`가 `SkinService.Changed`를 직접 구독해서, 목록에서 고르는 순간 이미 만들어 둔 재질의 색만 바꾼다(큐비를 다시 짓지 않는다) — 그래서 고른 게 바로 눈에 들어온다. 화면이 숨어 있는 동안 스킨이 바뀌었을 경우를 위해, 다시 보일 때(`OnEnable`)도 한 번 더 지금 스킨을 강제로 입힌다.

**연습 화면은 매번 새로 짓기 때문에 신경 쓸 게 없었지만, 실물 큐브 입력 화면은 앱을 켤 때 한 번만 만들어지고 계속 살아 있다.** 이 화면에서 스킨 변경 이벤트를 따로 구독하지 않으면, 설정에서 스킨을 바꾸고 돌아왔을 때 전개도 색이 예전 스킨 그대로 남는다. 이 화면만 별도로 `SkinService.Changed`를 구독해 전개도 칸과 배경, 색 스와치를 다시 칠하게 했다.

**이미지 텍스처 스킨 — 우드 (2026-08-07, 뒤이어 진행)**

발주서대로 만들어진 "우드" 스킨(`delivery/skins/wood/`)을 받고 나서, 자체 보고서를 그대로 믿지 않고 픽셀을 직접 읽어 재검증했다 — `representativeHex`가 실제 이미지 평균과 오차 0.5 이내로 정확했고, 6면 구분 하드 룰(휘도차 0.12 / 색상각 25도)도 15개 쌍 전부 재계산해서 통과를 확인했다. 다만 색 자체는 갈색 계열이 아니라 클래식 스킨과 같은 배색에 나뭇결만 입힌 것이었다 — 6면 구분 규칙을 통과시키는 안전한 선택이었을 것이다. 라이선스는 CC0가 아니라 AI 생성물(OpenAI 이용약관, 생성물 소유권은 사용자)이었는데, 상업적 이용 자체는 허용되는 조건이라 그대로 쓰기로 했다.

`Skin`에 `StickerTextures[6]`를 추가했다(비어 있으면 기존 색만 쓰는 스킨으로 동작 — 기존 5종은 그대로다). 텍스처가 있는 면은 재질 틴트를 흰색으로 둔다 — 틴트를 대표색으로 남겨 두면 텍스처 위에 색이 한 번 더 곱해져 실제보다 탁하고 어둡게 보인다. `SkinImporter` 에디터 스크립트가 `delivery/skins/*/meta.json`을 읽어 텍스처를 `Assets/Resources/SkinTextures/`에 복사하고 스킨 에셋을 만든다 — 다음 스킨이 도착해도 같은 스크립트로 붙는다.

2D 전개도·실물 큐브 입력 화면은 손대지 않았다. 거기는 처음부터 `StickerColors`(대표색)만 쓰도록 짜여 있어서, 텍스처가 생겨도 자동으로 그 대표색을 계속 보여준다.

### Phase F — 화면 전면 개편과 조작 손질 (2026-08-08 ~ 08-09)

화면 전체를 다시 그렸다. 공용 부품(`UiKit`)에 카드·스크롤 목록·아이콘판·헤더·소프트 아웃라인을 넣고, 글자 크기를 `UiMetrics` 상수로 모았다. 아이콘은 Tabler Icons(MIT) 비트맵을 쓰고, 홈 화면의 큐브 그림과 2×2/3×3/4×4 선택 이미지는 전용 아트로 교체했다. `SafeAreaFitter`가 모든 화면을 카메라 홀과 제스처 영역 안쪽으로 밀어 넣는다.

그 위에 아래를 손봤다. 대부분 **직접 만져 보고 나서야 드러난 것들**이다.

**큐브를 화면 한가운데로.** 연습 화면은 전개도가 화면 중앙을 카드로 차지하고 큐브가 위로 밀려 있었다. 전개도 기본값을 펼침에서 **접힘**으로 바꾸고 스크램블 카드 바로 아래 얇은 띠로 올렸다(`NetTop`/`NetCollapsedBottom`). 접혀 있어도 "펴기"로 언제든 부를 수 있고, 힌트가 칸을 강조할 때 쓸모가 있어 없애지는 않았다. 비워진 가운데에 맞춰 큐브 띄우는 비율도 0.18 → 0.04로 내렸다.

단계 학습 화면은 사정이 달랐다. 설명을 읽을 때는 코치 카드·페이지 넘김·공식 목록이 다 필요하지만, **「연습하기」를 눌러 직접 맞추는 동안에는 그것들이 자리만 차지한다.** 그래서 그 셋을 `ExplainGroup` 하나로 묶고 연습 중에는 통째로 숨긴 뒤 큐브를 키워(0.72 → 0.95) 가운데로 옮긴다(`RefreshPracticeLayout`). 상태 카드와 아래 버튼은 연습 중에도 필요하므로 묶음 밖에 뒀다.

**큐브가 미묘하게 삐뚤어 보이던 것.** 기본 시점이 `Euler(-22, 34, 0)`이었다. 야로 34도는 45도에서 어긋나 있어서 앞면과 오른쪽 면의 폭이 다르게 보인다 — 아무리 손으로 맞춰도 "뭔가 틀어졌다"는 인상이 가시지 않는 원인이었다. `Euler(-28, 45, 0)`으로 바꿔 두 면이 같은 폭으로 보이는 대칭 구도를 만들었다.

**손가락 회전이 버튼과 속도가 달랐던 것 — 이번 라운드에서 제일 컸다.**

증상은 "빨리 밀면 빨리 돌고 천천히 밀면 천천히 돈다"였다. 원인은 드래그 중에 `UpdatePreview`가 피벗을 **손가락 위치로 직접** 돌리고 있었기 때문이다(`끌린 픽셀 × DegreesPerPixel`). 즉 회전 속도가 곧 손 속도였다. 반면 버튼은 미리보기 없이 `LayerRotator`로 바로 가서 설정된 시간(기본 220ms)대로 돈다.

미리보기를 없애고, **스와이프 방향이 정해지는 순간 버튼과 똑같이 `_rotator.Enqueue(_move)`로 넘기게** 했다. 방향은 이미 `SwipeResolver`가 무브에 넣어 주므로(드래그 부호까지 반영) 따로 계산할 것이 없었다 — 미리보기가 쓰던 `_dragSign`은 순전히 겉모습용이었다.

부수 효과가 컸다. 미리보기 피벗을 만들고 되돌리고 떼어내던 코드가 통째로 필요 없어져 `TouchController`가 214줄 → 146줄이 됐고, `LayerRotator.EnqueueFromAngle`·`Pending.StartAngle`, 설정의 `SnapAngle`·`DegreesPerPixel`도 같이 사라졌다. **예전에 "돌리다 중간에 멈추면 큐브가 깨지던" 버그가 살던 코드가 정확히 여기였으므로, 그 위험도 함께 없어졌다.**

대신 성격이 하나 바뀌었다: 문턱을 넘기면 그 자리에서 회전이 확정되므로 손을 되돌려 취소할 수 없다. 그래서 `DragStartFraction`(화면 대각선의 2%, 이 폰에서 약 52px)이 이제 **"얼마나 밀어야 한 번 돌아가는가"**를 정하는 값이 됐다. 헛돌면 올리고 잘 안 돌면 내린다.

검증은 스크린샷 두 장으로 했다. 80ms짜리 빠른 스와이프를 주고 150ms 뒤에 찍으면 **아직 돌고 있고**, 1200ms짜리 느린 스와이프 중 800ms 시점에 찍으면 **이미 다 돌아 있다**. 손가락과 회전이 끊어졌다는 뜻이다. 두 경우 모두 정확히 한 번만 돌았다(뒤이어 찍은 화면과 해시가 같다).

**밖에서 가져온 것을 고지하지 않고 있었다.** 아이콘이 Tabler Icons(MIT)인데 저장소에 `LICENSE.txt`만 있고 README·스토어 문안 어디에도 저작권 문구가 없었다. MIT는 배포물에 그 문구를 함께 넣도록 요구하므로 그대로 냈으면 라이선스를 어기는 것이었다. 8절과 스토어 문안에 넣고, "남은 일"에 출시 전 확인 항목으로 박아 뒀다.

정리도 했다. 디자인 검수 스크린샷(24MB)·이미지 생성 스크래치·로그 25개가 커밋을 기다리고 있어서 `.gitignore`로 걸렀고, 서명키(`*.keystore`, `*.jks`)가 실수로 들어가지 않게 하는 규칙도 미리 넣었다.

핵심 시험 몇 가지:

- 같은 층을 네 번 돌리면 제자리 (모든 크기 × 모든 축 × 모든 층)
- 임의 시퀀스 + 역순 = 제자리
- 어떤 회전 뒤에도 각 색의 칸 수가 정확히 N²개
- `R U R' U'` 여섯 번 = 제자리, 그전에는 아님
- 애니메이션이 끝나면 모든 스티커가 논리 상태가 말하는 자리에 물리적으로 있다
- 어떻게 섞어도 유효성 검사를 통과하고, 스티커 하나만 비틀면 거부한다
- **힌트를 따라가면 실제로 풀린다**
- 각 단계의 연습 시작 상태가 정확히 앞 단계까지만 통과한 상태다

```bash
"C:/Users/사용자/AppData/Local/Unity/Editors/6000.3.18f1/Editor/Unity.exe" -runTests -batchmode -nographics -projectPath "C:/workAndroid/3Dcube" -testPlatform EditMode -testResults "TestResults-EditMode.xml" -logFile -
```

## 6. 실기기에서만 드러난 것들

에디터 테스트가 전부 통과하고 APK도 빌드됐는데, **폰에 깔자 첫 화면부터 깨졌다.** 한 번의 실기기 실행이 아홉 가지를 드러냈다. 전부 빌드에만 존재하는 조건이거나 눈으로 봐야 아는 종류라, 테스트를 아무리 늘려도 재현되지 않는다.

| 증상 | 원인 |
|---|---|
| 모든 화면이 겹쳐 보임 | 셰이더 예외로 `Go(홈)`에 도달하지 못함 |
| `Shader.Find`가 null | 어떤 애셋도 URP Lit을 참조하지 않아 빌드에서 잘림 |
| 스티커가 안 보임 | `CreatePrimitive(Quad)`가 잘려나간 `MeshCollider`를 붙이려다 실패 |
| 큐브가 화면을 뒤덮음 | 시야각은 세로 기준인데 세로 화면은 가로 폭이 훨씬 좁다 |
| 이전 화면이 유령처럼 남음 | 카메라 `rect`를 주면 **그 밖은 지워지지 않는다** |
| 노테이션 패드가 화면을 가림 | 컴포넌트가 자기 자신을 부모로 삼고 앵커를 덮어씀 |
| 섞으면 큐비가 흩어짐 | 20수를 애니메이션 큐에 밀어넣어 큐 넘침과 중간 중단이 얽힘 |
| 학습 화면에서 큐브가 정면만 보임 | `OrbitCamera.Init`을 부르지 않아 기본 시점이 안 잡힘 |
| 기록 화면에 돌아가기 버튼 없음 | 안드로이드 뒤로가기 키로만 탈출 가능했다 |

**세로가 짧은 기기(2340)를 추가로 물리자** 학습 목록의 안내 문구가 7단계 버튼과 겹치는 것이 드러났다. 2400 화면에서는 여유가 있어 보이지 않던 문제다.

**손가락으로 돌릴 때의 문제들:**

- 반시계 회전에서 미리보기는 −90°로 도는데 애니메이션은 +270°로 돌아, 손을 떼면 큐브가 먼 길로 튀었다. 끝 자세는 같지만 가는 길이 달랐다
- 큐비 몸통을 0.96배로 줄여 놨더니 사이가 벌어져, 층이 돌 때 아홉 조각이 따로 노는 것처럼 보였다. 딱 붙여 한 덩어리로 만들었다
- **돌리다 중간에 멈추면 큐브가 깨졌다.** 자세를 직각으로 맞추는 코드가 회전축을 성분별로 반올림했다. 30°쯤 돌아간 방향 (0.5, 0, 0.87)이 (1, 0, 1)이 되어 축이 아닌 대각선이 나오고, 큐비가 45° 틀어진 채 굳었다. 가장 가까운 축 하나로 붙이도록 고치고, 취소할 때는 아예 피벗을 0°로 되돌린 뒤 떼어내게 했다
- **테마를 바꾸면 배경만 밝아지고 버튼은 어두운 채로 남았다.** 색이 만들 때 한 번 박히기 때문이다. 테마가 바뀌면 화면을 다시 짓는다

### 실기기 확인 목록

자동화할 수 없는 항목은 [`docs/device-checklist.md`](docs/device-checklist.md)에 있다.
스와이프의 "손에 붙는 느낌"은 기계가 판단할 수 없고, 터치 입력을 흉내 내는 비용은 얻는 것에 비해 크다.

조작이 뻑뻑하거나 예민하면 코드가 아니라 `Assets/Resources/TouchInputSettings.asset` 값을 조정한다 — 드래그 시작 거리, 스냅 각도, 픽셀당 각도, 터치 여유 반경이 거기 있다.

## 9. 사용해 보고 고친 것들

실제로 만져 본 뒤 들어온 의견과 대응.

| 의견 | 대응 |
|---|---|
| 돌리다 멈추면 큐브가 깨진다 | 자세 스냅 계산을 고침 (위 6절) |
| 조각들이 따로 도는 느낌 | 큐비를 딱 붙이고 스티커를 표면에 얹음 |
| 회전이 너무 빨라 안 보인다 | 기본 애니메이션 120ms → 220ms, 설정 범위 0~400ms |
| 전개도가 거슬린다 | 연습 화면에 접기 버튼 추가, 설정에 저장 |
| 밑면으로 돌리기 힘들다 | 두 손가락으로 어디서나 시점 회전 |
| 버튼이 안 예쁘다 | 코드로 그린 둥근 모서리 스프라이트를 전체 적용, 누름 표시 추가 |
| 글로만 설명하지 말고 어디를 어떻게 바꾸는지 | 단계 화면에 힌트 버튼 — 다음 수를 알려주고 큐브가 직접 돌려서 보여준다 |
| 큐브 겉모습을 바꾸고 싶다 | 스킨 6종(색 5종 + 나뭇결 텍스처 1종), 설정 → 큐브 스킨 |
| 전개도가 쓸데없이 자리를 차지한다 | 기본을 접힘으로, 위쪽 얇은 띠로 이동. 큐브가 화면 한가운데를 넓게 쓴다 |
| 배우기에서도 큐브가 가운데 왔으면 | 연습 중에는 설명 요소를 숨기고 큐브를 키워 가운데로 |
| 큐브가 처음부터 미묘하게 틀어져 있다 | 기본 시점 야로 34° → 45°. 두 면이 같은 폭으로 보인다 |
| 손으로 돌리면 손 속도대로 돌아간다 | 미리보기를 없애고 버튼과 같은 경로로. 이제 어떻게 밀든 설정된 시간대로 돈다 |
| 글자 크기가 제각각이다 | 나란히 있는데 달랐던 것부터 통일, 크기를 `UiMetrics` 상수로 모음 |
